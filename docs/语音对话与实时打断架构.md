# Chatchat 语音对话与实时打断架构

更新时间：2026-04-27

本文档描述当前语音链路的真实实现和后续演进方向。当前版本已经不再以本地 ASR/TTS 模型为目标，而是采用：

- 语音输入：百炼/DashScope ASR API
- 云端音色：百炼/DashScope TTS API
- 本机音色：浏览器 `SpeechSynthesis`
- 播放控制：前端维护播放状态、停止和中断

后端不加载本地语音模型，不需要 GPU，也不需要为 ASR/TTS 预留显存。

## 1. 当前目标

语音功能分成两条链路：

- 语音输入：用户录音后转成文本，填入对话框或直接发送
- 语音播放：assistant 回复可以用本机音色或阿里云音色播放

当前优先级：

1. 保持文本聊天流稳定，不把音频二进制混进聊天 `NDJSON`
2. 支持用户在设置页选择“本机音色”或“阿里云音色”
3. 支持消息级播放、停止、切换会话时清理播放
4. 后续再演进到边生成边分句播报和用户插话打断

## 3. ASR 链路

```text
浏览器录音
  -> POST /api/audio/transcribe
  -> 后端大小/时长/音量校验
  -> DashScope ASR API
  -> 返回文本
```

相关配置：

```env
AUDIO_TRANSCRIPTION_ENABLED=true
AUDIO_TRANSCRIPTION_MODEL=qwen3-asr-flash
AUDIO_TRANSCRIPTION_TIMEOUT_SECONDS=60
AUDIO_TRANSCRIPTION_API_MAX_BYTES=10485760
AUDIO_TRANSCRIPTION_LANGUAGE=zh
AUDIO_TRANSCRIPTION_MIN_DURATION_MS=300
AUDIO_TRANSCRIPTION_MIN_RMS_DBFS=-65
```

默认鉴权：

- 优先使用 `AUDIO_TRANSCRIPTION_API_KEY`
- 留空时使用 `DASHSCOPE_API_KEY`

默认地址：

- 优先使用 `AUDIO_TRANSCRIPTION_BASE_URL`
- 留空时使用 `DASHSCOPE_BASE_URL`

`AUDIO_TRANSCRIPTION_BASE_URL` 和 `AUDIO_TRANSCRIPTION_API_KEY` 主要用于以后单独给 ASR 配代理、网关或独立账号。当前全部走百炼时可以留空。

## 4. TTS 链路

### 4.1 本机音色

```text
assistant 文本
  -> 浏览器 SpeechSynthesis
  -> 系统音色播放
```

特点：

- 不经过后端
- 不消耗百炼 TTS API
- 音色由用户设备和浏览器决定
- 适合低成本兜底

### 4.2 阿里云音色

```text
assistant 文本
  -> POST /api/audio/speech
  -> DashScope TTS API
  -> 返回音频 URL / 元数据
  -> 前端播放音频
```

请求体：

```json
{
  "text": "要播放的文本",
  "voice": "longanyang",
  "rate": 1
}
```

返回体：

```json
{
  "url": "https://...",
  "content_type": "audio/mpeg",
  "model": "cosyvoice-v3-flash",
  "voice": "longanyang"
}
```

相关配置：

```env
AUDIO_TTS_ENABLED=true
AUDIO_TTS_MODEL=cosyvoice-v3-flash
AUDIO_TTS_VOICE=longanyang
AUDIO_TTS_FORMAT=mp3
AUDIO_TTS_SAMPLE_RATE=24000
AUDIO_TTS_TIMEOUT_SECONDS=60
AUDIO_TTS_MAX_CHARS=3000
```

默认鉴权：

- 优先使用 `AUDIO_TTS_API_KEY`
- 留空时使用 `DASHSCOPE_API_KEY`

默认地址：

- `AUDIO_TTS_BASE_URL` 默认是百炼语音合成接口
- 只有改代理、网关或自定义 endpoint 时才需要覆盖

## 5. 播放偏好

设置页需要表达的是“播放来源”，不是“模型部署位置”：

- 本机音色：浏览器系统音色
- 阿里云音色：DashScope TTS 音色

推荐保存的偏好：

- `speechProvider = browser | dashscope`
- `browserVoiceURI`
- `cloudVoice`
- `rate`
- `autoPlayAssistant`

这样后续即使新增其他云厂商，也可以继续沿用同一个播放来源模型。

## 6. 打断与停止

当前最重要的打断场景：

- 用户点击停止播放
- 用户开始新的录音
- 用户切换会话
- 用户重试回答
- 用户删除或切换当前消息

推荐统一进入同一个清理过程：

1. 停止当前 `HTMLAudioElement` 或 `SpeechSynthesis`
2. 取消未完成的 `/api/audio/speech` 请求
3. 清空当前消息的播放状态
4. 如果当前聊天仍在生成，按用户动作决定是否同时调用 chat stop

语音播放不应该反向污染聊天文本流。播放失败只影响播放按钮状态，不应该导致 assistant 文本消息失败。

## 7. 后续准流式播报

如果要支持 assistant 一边输出一边播放，推荐仍然由前端做分句：

```text
LLM token stream
  -> 前端文本增量缓冲
  -> 句子闭合
  -> 根据 speechProvider 选择浏览器朗读或 /api/audio/speech
  -> 播放队列
```

建议句子边界：

- `。`
- `！`
- `？`
- `!`
- `?`
- 连续换行
- 长度阈值触发的软切分

建议阈值：

- `soft_max_chars_per_segment = 80`
- `hard_max_chars_per_segment = 140`

后端不需要为了第一版准流式播报维护聊天切句状态。这样可以保持聊天流、音频播放和打断控制彼此解耦。

## 8. 资源影响

当前语音链路不占 GPU 显存。服务器侧资源主要来自：

- 上传音频的内存暂存
- WAV 元信息解析和 RMS 计算
- 调用 DashScope API 的 HTTP 连接
- TTS 返回 URL 后的少量状态处理

三五个人使用时，语音通常不是本机瓶颈。真正需要关注的是：

- `AUDIO_TRANSCRIPTION_API_MAX_BYTES` 不要放太大
- `AUDIO_TTS_MAX_CHARS` 控制单次合成文本长度
- 前端自动播报不要无限排队
- 外部 API 超时要可见，不要卡住 UI

## 9. 当前结论

当前最稳的路线是：

1. 保持聊天 `NDJSON` 文本流不变
2. ASR 走 DashScope API
3. TTS 在“浏览器本机音色”和“DashScope 云端音色”之间切换
4. 前端负责播放队列、中断和状态清理
5. 后续准流式播报先从前端分句开始，不引入后端音频流协议

这条路线适合纯 CPU 服务器，也方便后续替换或增加其他云端语音供应商。
