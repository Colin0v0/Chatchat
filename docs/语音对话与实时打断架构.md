# Chatchat 语音对话与实时打断架构

更新时间：2026-04-23

## 1. 目标

这份文档针对当前 `Chatchat` 的真实代码结构，定义一条尽量不返工的语音演进路线：

- 先支持本地 `TTS`，让 assistant 回复可以播放语音
- 再支持“按句分段”的准流式朗读
- 最后支持用户插话时的实时打断（`barge-in`）

当前约束：

- 开发机显卡为 `RTX 4060`
- 预期只给本地 `TTS` 预留约 `4GB` 显存
- 当前系统已经有：
  - 文本聊天流式输出
  - 录音输入
  - 本地语音转写
- 当前系统还没有：
  - 本地 `TTS`
  - assistant 语音播放队列
  - 语音会话级中断控制

## 3. 设计原则

### 3.1 不改现有文字流主链

当前文本回复主链已经稳定：

- 后端输出 `NDJSON`
- 前端按 `meta / status / reasoning / token / done / error` 消费

第一阶段不要把二进制音频直接塞进现有聊天流。原因：

- 文字流目前已经清晰、可恢复、可重连
- 往 `NDJSON` 里混音频分片会让前后端协议快速复杂化
- 实时打断真正需要的是“可取消的语音任务”，不是“文字流里顺便带音频”

结论：

- 文本流继续走当前 `NDJSON`
- `TTS` 作为独立音频通道
- 前端负责把文本流拆句后送到 `TTS`

### 3.2 先做“分句可取消”，不要直接追求逐 token 播放

在 `4GB` 显存预算下，最实用的目标不是“每个 token 都即时发声”，而是：

- 文本仍然流式显示
- 前端检测到句子边界
- 每一句单独发给本地 `TTS`
- 前端维护播放队列
- 用户开口时立即清空队列并停止播放

这样得到的是“准实时打断”的体验，复杂度和稳定性都更可控。

### 3.3 语音层必须有自己的会话标识

后续一旦支持：

- 停止生成
- 重新生成
- 用户插话
- 切换会话

就必须能判断一段音频是否还属于当前这次对话。

因此语音层从第一版起就应该引入：

- `speech_session_id`
- `utterance_id`
- `segment_index`

哪怕第一版只是前端本地维护，也要按这个概念设计。

## 4. 推荐演进路线

## 4.1 Phase 1：回复完成后播放

### 目标

- assistant 回复完成后，用户点击按钮播放整段语音
- 本地 `TTS` 先只支持短文本整段合成
- 不追求边生成边播

### 实现方式

- 后端新增 `POST /api/audio/tts`
- 请求体只包含：
  - `text`
  - `voice`
  - `format`
- 返回 `audio/wav` 或 `audio/mpeg`
- 前端在 assistant 消息操作区加“播放”按钮

### 价值

- 最快验证本地 `TTS` 模型是否适合当前机器
- 不碰聊天流协议
- 能先把音色、速度、格式、缓存策略跑通

## 4.2 Phase 2：按句分段播放

### 目标

- 文本仍然流式显示
- assistant 一边输出，前端一边按句切分
- 句子一旦闭合，就触发一次 `TTS`
- 合成好的语音片段进入播放队列

### 推荐职责划分

前端负责：

- 接收文本流
- 维护未闭合句缓冲
- 识别句边界
- 发起逐句 `TTS` 请求
- 管理音频播放队列

后端负责：

- 接收短文本 `TTS` 请求
- 串行或低并发执行本地合成
- 返回音频数据

### 为什么前端拆句更适合当前项目

因为当前文本流已经在前端稳定消费，直接在前端做句子缓冲：

- 不需要改 `backend/app/runtime/stream_codec.py`
- 不需要改聊天运行态存储协议
- 不需要让后端同时维护“文本流状态 + 语音切句状态”
- 用户点击停止时，前端可以同时：
  - 停止当前聊天请求
  - 中止正在合成的 `TTS` 请求
  - 清空待播放队列

### 建议的句子边界

把以下内容视为“可送去合成”的边界：

- `。`
- `！`
- `？`
- `!`
- `?`
- 连续换行
- 长度阈值触发的软切分

建议增加两个阈值：

- `soft_max_chars_per_segment = 80`
- `hard_max_chars_per_segment = 140`

含义：

- 正常优先按标点切
- 如果长时间没有闭句标点，就在安全位置切一刀

## 4.3 Phase 3：实时打断

### 目标

用户在 assistant 播报中途一开口，系统立刻：

- 停止当前音频播放
- 中断尚未完成的 `TTS`
- 必要时中止当前 LLM 回复
- 切回“听用户说”的状态

### 这不是单个按钮功能，而是状态机

建议语音会话状态至少包含：

- `idle`
- `listening`
- `transcribing`
- `thinking`
- `speaking`
- `interrupted`

关键状态转移：

- `thinking -> speaking`
  - 第一段可播放语音就绪
- `speaking -> interrupted`
  - 检测到用户重新开口
- `interrupted -> listening`
  - 播放停止、队列清空、转入采集输入

### 打断优先级

发生打断时，建议按下面顺序执行：

1. 前端立即暂停并重置 `HTMLAudioElement`
2. 取消前端所有未完成 `TTS` 请求
3. 清空本轮 `speech_session_id` 的待播放片段
4. 如仍在文本生成中，执行现有 `chat stop`
5. 进入新的录音/转写会话

这一顺序的核心目标是：先让用户“听不到旧回答”，再清理后端任务。

## 5. 音频链路设计

### 5.1 推荐的第一版链路

```text
LLM token stream
  -> 前端文本缓冲
  -> 句子闭合
  -> POST /api/audio/tts
  -> 返回单句音频
  -> 前端排队播放
```

### 5.2 暂不推荐的链路

```text
LLM token stream
  -> 后端同步切句
  -> 后端同时做 TTS
  -> NDJSON 中混合音频元数据或二进制引用
  -> 前端再解释播放
```

这个方向不是不能做，而是不适合作为第一步。它会把：

- 聊天流
- 音频流
- 中断控制
- 恢复重连

一起耦合到当前运行态协议里，改动面过大。

## 6. 后端建议

## 6.1 新增 `TTS` 服务抽象

参考当前 `AudioTranscriber` 的组织方式，建议新增：

- `backend/app/audio/synthesizer.py`
- `backend/app/audio/segmentation.py`

并把 `backend/app/audio/state.py` 扩成：

- `transcriber`
- `synthesizer`

### 建议的服务接口

```python
class AudioSynthesizer:
    def synthesize(
        self,
        *,
        text: str,
        voice: str,
        format: str = "wav",
        rate: float = 1.0,
    ) -> bytes:
        ...
```

第一版只做同步合成即可，不需要先上复杂流式接口。

## 6.2 路由建议

在 `backend/app/api/audio.py` 增加：

- `POST /api/audio/tts`

第一版建议参数：

- `text`
- `voice`
- `format`
- `rate`

返回：

- `audio/wav`

为什么先选 `wav`：

- 调试简单
- 前端不需要额外解码链路
- 本地开发时问题更容易定位

后续如果要减小传输体积，再补 `mp3`

## 6.3 配置建议

在 `backend/app/core/config.py` 增加独立配置，而不是复用转写配置：

- `audio_tts_enabled`
- `audio_tts_backend`
- `audio_tts_model`
- `audio_tts_device`
- `audio_tts_voice`
- `audio_tts_max_chars`
- `audio_tts_max_concurrency`
- `audio_tts_eager_load`

建议默认值倾向保守：

- `audio_tts_enabled = false`
- `audio_tts_device = "cuda"` 或 `"cpu"` 由环境决定
- `audio_tts_max_concurrency = 1`

## 6.4 显存预算建议

如果只预留约 `4GB` 给本地 `TTS`：

- `TTS` 单并发
- 每次只合成一个短句
- 长文本拆句
- 空闲时支持模型卸载

并且保持当前转写默认在 `CPU`：

- `audio_transcription_device = "cpu"`

这样可以避免：

- `ASR` 和 `TTS` 抢同一块小显存
- 播报中途再开转写时显存抖动过大

## 7. 前端建议

## 7.1 新增独立语音播放 Hook

建议新增：

- `frontend/src/features/chats/model/useSpeechPlayback.ts`

职责：

- 维护 `speech_session_id`
- 维护待合成句队列
- 维护待播放音频队列
- 暴露：
  - `enqueueTextSegment`
  - `playMessage`
  - `interrupt`
  - `stopAll`

这个 Hook 不要并入 `useConversationStreams.ts`，避免文本流状态和音频播放状态互相污染。

## 7.2 在 `useConversationStreams.ts` 只做一件事：产出稳定文本

`useConversationStreams.ts` 的职责仍然应该是：

- 处理聊天流式事件
- 把 assistant 文本和 reasoning 写回消息状态

如果要支持按句播报，建议只在这里增加一个很轻的输出：

- 对外暴露“assistant 新增文本片段”

真正的切句和 TTS 调度仍交给 `useSpeechPlayback.ts`

## 7.3 打断触发点

以下行为都应该调用统一的 `interrupt()`：

- 用户点击停止
- 用户开始新的录音
- 用户切换到其他会话
- 用户重试回答
- 用户编辑并重新提交消息

这样“谁触发了中断”可以不同，但语音层只有一套清理逻辑。

## 7.4 消息级与会话级两层能力

建议区分两种播放入口：

- 消息级：点某条 assistant 消息上的播放按钮
- 会话级：对当前流式回复自动播报

不要一开始就把两者混成一个开关。这样更方便：

- 单独调试消息播放
- 再逐步上线自动播报

## 8. 推荐的一期到三期改造顺序

## 8.1 一期

- 后端新增本地 `TTS` 抽象与 `/api/audio/tts`
- 前端在 assistant 消息上增加“播放”按钮
- 整段文本播放

## 8.2 二期

- 前端增加 `useSpeechPlayback.ts`
- 把文本流按句缓冲
- 合成短句并排队播放
- 支持手动停止与自动清队

## 8.3 三期

- 录音一开始就触发 `interrupt()`
- 停播、停合成、停生成统一联动
- 再评估是否需要真正的实时 `ASR`

## 9. 模型建议

在当前目标下，推荐把第一版 `TTS` 供应商抽象为可替换接口，默认先接轻量本地方案。

建议：

- 第一版优先轻量中文 `TTS`
- 重点看：
  - 启动成本
  - 单句延迟
  - 显存稳定性
  - 中文停顿和断句自然度

当前目标不是声音克隆，也不是多角色拟真，因此“稳定、可取消、低资源占用”比极致音色更重要。

## 10. 当前最推荐的落地结论

对现在这个项目，最稳的路线是：

1. 保持现有聊天 `NDJSON` 文本流不变
2. 后端单独新增本地 `TTS` 接口
3. 前端新增独立语音播放 Hook
4. 二期通过前端分句实现准流式播报
5. 三期把“录音开始”接到统一 `interrupt()` 上

这条路线的优点是：

- 不会推翻当前聊天流架构
- 与当前 `useChatApp + useConversationStreams + audio API` 结构对齐
- 适合 `4060 + 4GB TTS 显存预算`
- 后续可以平滑升级到实时打断
