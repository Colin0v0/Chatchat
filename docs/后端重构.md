# Chatchat Backend Refactor Plan

## 0. 当前迁移状态（2026-04-27）

这份文档下面的大段内容，保留了最初的诊断和目标设计；但代码已经继续迁移了不少。为了避免你读到旧描述时误判，先看当前真实状态：

- 已完成：
  - 基础设施已经切到 `PostgreSQL + pgvector + Redis + Alembic`
  - 新后端骨架已经建立：`app/application`、`app/runtime`、`app/providers`、`app/tools`
  - 聊天主链已经迁到统一 runtime orchestrator，旧 `app/chat/workflow.py`、`app/chat/streamer.py` 已删除
  - debate 流式执行已经迁到 `app/runtime/modes/debate.py`，旧 debate wrapper 已删除
  - `app/runtime/modes` 已经补出正式 `base + registry`，`chat` / `debate` 都通过 mode runtime 注册，不再由 application 层直接绑定具体实现文件
  - debate mode 内部的大块执行逻辑已经从 `runtime/modes/debate.py` 拆到 `runtime/modes/debate_execution.py`
  - debate mode 的 stage 推进、judge question 落库、decision finalize、`stage_changed` 事件生成，已经继续拆到 `runtime/modes/debate_state.py`
  - debate mode 的 action handler 已继续拆到 `runtime/modes/debate_actions.py`，`debate.py` 现在只保留 mode 注册与 action dispatch
  - debate action 内部的规则与流程步骤已继续下沉到 `runtime/modes/debate_policies.py` 和 `runtime/modes/debate_steps.py`，`debate_actions.py` 现在主要承担 mode 级编排
  - debate runtime 已继续拆出 stage handler：`runtime/modes/debate_stage_handlers.py` 负责 stage follow-up / judge evaluation / decision summary，`runtime/modes/debate_turn_handlers.py` 负责 next/question 的 turn loop
  - 底层模型流式执行已经抽成 `app/runtime/model_runner.py`，chat 和 debate 共享同一套 provider/thinking/流式归一化逻辑
  - provider-specific request payload / stream decode 语义已经抽到独立 `app/provider_codecs/*`，`app/llm` 现在主要只保留 capability / thinking / SSE 等通用抽象
  - 主后端运行链已经新增 `app/provider_transports/*`；`providers/*`、附件上传、reranker 主链不再直接 import `app.llm.*_client`

  - 旧 `app/llm/openai_client.py`、`gemini_client.py`、`claude_client.py` 兼容壳已经删除，相关测试已切到 `provider_transports/provider_codecs`
  - `memory/extractor.py`、`retrieval/query_rewrite.py`、`retrieval/websearch/translator.py` 已从旧 `app.llm` 兼容层摘出，直接改走 runtime 级模型执行助手
  - `memory/store.py` 的非 SQLite 召回路径已经从 Python 全量扫描改成数据库内打分/排序，PostgreSQL-first 方向更明确
  - `app.llm` 包级导出已不再承载业务侧 `complete_chat/stream_chat` 入口，`llm/service.py` 已删除
  - `storage/sqlite_legacy.py` 已删除，SQLite legacy patch 不再处于主启动链路
  - `storage/database.py` 已改成 PostgreSQL-first 启动校验；默认 `DATABASE_URL` 和部署环境变量都已切到 PostgreSQL，不再默认落回 SQLite
  - `KnowledgeChunk` 已从 `embedding_json` 切到 vector 主列，Alembic 已新增 pgvector 迁移；知识库在 PostgreSQL 下开始走数据库向量检索路径
  - `KnowledgeService.retrieve_context()` 已正式接入 `tag:` / `path:` / `folder:` 查询过滤，不再只是普通文本检索
  - PostgreSQL 知识库检索已从“纯向量候选”推进到“向量候选 + 数据库侧关键词候选融合”，并且相邻 chunk 会从数据库真实补回，不再只在候选集内部做残缺的 neighbor expansion
  - Alembic 已新增 knowledge chunk 检索索引迁移：`user_id + path + chunk_index`、`ivfflat(vector_cosine_ops)`、`GIN trigram search text`
  - `MessageAttachment.upstream_file_id` 已从主模型删除，附件远端上传缓存正式统一到 `provider_file_refs`；Alembic 已补删列迁移
  - 检索不再走旧 `RetrievalService`，而是进入新的 `ToolRuntimeService`
  - 模型目录已经切成 capability-first，`app/providers/catalog.py` 是唯一真源
  - `/api/models` 已开始向前端暴露更完整的 capability / reasoning 元数据，不再只给少量布尔位
  - chat / regenerate 的显式推理控制已经从简单 `thinking_enabled` 升级到 `reasoning_profile`
  - provider adapter 到 `app/llm/*_client.py` 的 transport 层之间，已经开始直接传递 `reasoning_profile`，不再先退化成布尔值
  - `llm/thinking.py` 的 prompt 注入兼容逻辑也已改为直接基于 `reasoning_profile`
  - 旧 `app/llm/catalog.py`、`app/llm/registry.py`、`app/retrieval/plan.py`、`app/retrieval/service.py` 已删除
  - API 输入语义已经从 `retrieval_mode = none / rag / web` 迁到 `tool_mode = none / knowledge / search`
  - 启动链已经从 `ensure_schema_ready()` 收敛成 `initialize_storage()`，SQLite 不再带 legacy schema patch
  - 前端源码已开始同步：聊天/重试/辩论创建请求改发 `tool_mode`，不再继续沿用 `retrieval_mode`
  - 前端 composer 已补出正式 `reasoning_profile` 能力驱动控件；聊天发送与重试现在都会按模型 capability 透传 reasoning profile，而不是只保留后端接口字段
  - 本地模型推理链路已经移除：Ollama、`openai_local`、本地 OCR/vision、本地 ASR、本地 embedding、本地 reranker、模型 idle cache 都不再是运行时代码路径
  - RAG embedding / rerank、语音转写和云端 TTS 已统一走百炼/DashScope API；DeepSeek 聊天走 DeepSeek 官方 OpenAI-compatible API

- 当前仍未完成：
  - 知识库虽然已经补上 PostgreSQL 侧关键词融合、邻居补全和索引迁移，但整体仍然是“候选召回 + rerank + neighbor expansion”形态，还没有继续推进到更完整的数据库侧排序融合、查询分析和召回观测
  - 前端虽然已经补出 reasoning profile 正式交互，但还没有继续推进到更强的 capability-aware UI，例如按模型显示 reasoning summary/trace 差异、工具能力差异和输入模态能力提示
  - debate 虽然已经拆出 `execution/state/actions/policies/steps/stage_handlers`，但还没有进一步沉淀成更细的 stage policy / persistence policy / transition object，例如 `next/ask/decision` 各自独立的 stage context、free debate budget policy、judge summary persistence adapter
  - `app/llm` 虽然已经大幅收缩，但 `thinking.py` 里的 prompt 注入兼容仍然属于过渡方案；后续还需要继续把 reasoning 策略收敛成 provider capability + runtime policy，而不是保留模型特判
  - SQLite 仍然存在于一部分单元测试夹具里，作为轻量测试数据库；这不再是运行时主链，但测试基座后续还可以继续评估是否切到更接近 PostgreSQL 的方案

- 这轮之后的直接下一步：
  - 继续把 debate runtime 从 stage handler 推到更细的 stage context / transition object / persistence adapter，减少 `Session` 和 `DebateSession` 在 handler 中直接穿透

  - 继续让 README、部署文档和 catalog 保持同步，避免旧本地模型配置重新进入部署说明

## 1. 目标

这次后端重构的核心目标，不是把现有代码简单搬家，而是把下面几件事真正解耦：

- 模式编排：普通聊天、辩论、以后新增模式
- 模型接入：OpenAI-compatible / DeepSeek / Claude / Gemini / 未来新厂商
- 输入归一化：文本、图片、PDF、文件、以后音频/视频
- 推理控制：thinking / reasoning / budget / summary / trace
- 流式输出：文本、thinking、tool call、tool result、usage
- 工具层：RAG、Search、以后更多 app tools / provider-native tools
- 持久化：会话、消息、运行记录、附件、知识库、记忆

目标结果应该是：

- 新增同一 API 家族下的新模型时，只改模型目录，不改聊天主链路。
- 新增一个新厂商时，只新增一个 provider adapter，不改 chat/debate/retrieval 业务代码。
- 新增一个新模式时，只新增一个 mode plugin，不改 provider adapter。
- 前端短期不用一起大改，后端优先推进，必要时允许破坏式迁移。

## 2. 结合当前目录的现状诊断

### 2.1 主链路已经成型，但边界还不够硬

当前聊天主链路基本是：

- `app/api/chat.py`
- `app/chat/workflow.py`
- `app/chat/streamer.py`
- `app/llm/service.py`

这条链路可以跑，但 `chat/streamer.py` 里同时承担了：

- 历史裁剪
- 附件上下文准备
- retrieval 调用
- memory prompt 注入
- thinking 归一化
- provider stream 消费
- assistant message 落库

这意味着“编排层”和“模型接入层”还没有彻底分开。

### 2.2 provider 适配逻辑散落在多个层次

当前和模型差异有关的逻辑分散在：

- `app/llm/service.py`
- `app/llm/openai_client.py`
- `app/llm/gemini_client.py`
- `app/llm/claude_client.py`
- `app/llm/thinking.py`
- `app/chat/history.py`
- `app/chat/upstream_files.py`

具体表现：

- `llm/service.py` 用 provider 分支做总 dispatch。
- `chat/history.py` 根据 `native_multimodal` 决定是本地解析还是原生多模态。
- `llm/thinking.py` 里还有 prompt 注入式 thinking 兼容逻辑。
- `openai_client.py` 同时兼容 `openai`、`codex`、`trio`，但参数控制又不完全一样。

结果就是：加一个新模型，常常不只是加目录项，还要判断它属于哪种 thinking、多模态、文件上传、流式格式。

### 2.3 当前“thinking”抽象过弱

现在的控制入口基本还是：

- `thinking_enabled: bool | None`
- `thinking_mode: force_on / force_off / default_on / default_off`

这只能表达“开”或“关”，但厂商真实差异远不止这些。

当前已经出现的差异就包括：

- OpenAI 系 reasoning 更像 effort/profile
- Claude 更像 thinking budget + content block
- Gemini 更像 thoughts/thought signatures
- 本地模型有时只能靠 prompt 注入 `<think>`

所以 `thinking_enabled` 这个布尔值已经不够当后端内部协议了。

### 2.4 当前多模态抽象是“路由条件”，不是“统一输入模型”

当前 `ChatMessagePayload` 只有：

- `content`
- `images`
- `documents`
- `files`

这比直接拼字符串已经好很多，但仍然不够通用。现在的多模态差异主要通过 `native_multimodal` 这个枚举来控制：

- `false`
- `local`
- `codex`
- `gemini`
- `claude`

问题是这个字段本质上在表达“厂商特例”，不是“能力矩阵”。

例如一个模型真正需要描述的是：

- 图片支持吗
- PDF 支持吗
- 其他文件支持吗
- 接受 `inline base64` 还是 `file_id`
- 是否需要先上传到 provider
- 是否只能处理 PDF，不能处理 DOCX

这些能力现在被压缩进一个 `native_multimodal` 字段里，后面只会越来越难扩。

### 2.5 模式层已经开始分叉

当前有两套明显不同的运行链：

- `app/chat/*`
- `app/debate/*`

但 `debate/streaming.py` 和 `chat/streamer.py` 底层其实都还是在做：

- 组 prompt
- 调 `stream_chat`
- 消费 token / reasoning
- 持久化结果

这说明“模式”还没有被抽象为统一运行时上的 plugin，而是每种模式都自己长出一套半独立链路。以后再加模式，复杂度会继续线性上升。

### 2.6 工具层还停留在 retrieval mode，不是真正的 tool runtime

现在的工具语义主要还是：

- `retrieval_mode = none / rag / web`

这更像“回答前先不要查、查知识库、查网页”，而不是通用工具运行时。

当前 `RetrievalService` 做的是：

- 规划 retrieval
- 跑 RAG / Web Search / 文件上下文
- 把结果拼成 system message 注入

这对当前产品是能用的，但和未来真正的 tool loop 还不是一回事。后面如果要接：

- model-driven tool call
- provider-native tools
- 多轮工具调用
- tool result 回填再继续推理

现在这套 `retrieval_mode` 会成为阻力。

### 2.7 数据库层问题已经开始影响架构

当前数据库问题不是单点，而是几类问题叠加：

#### 1. 运行时迁移

`app/storage/database.py` 在启动时：

- `create_all`
- `ALTER TABLE IF NOT EXISTS` 风格补列
- 修补旧数据

这适合早期迭代，不适合继续演进。模式、run、tool trace 一多，运行时补 schema 会很危险。

#### 2. JSON/Text 字段承担了太多职责

当前典型字段包括：

- `messages.sources_json`
- `messages.context_json`
- `messages.brainstorm_json`
- `debate_sessions.config_json`
- `debate_sessions.summary_json`
- `debate_turns.sources_json`
- `knowledge_chunks.embedding_json`

这些字段让数据结构短期很灵活，但后面做查询、回放、统计、迁移、兼容都会越来越重。

#### 3. conversation 只记录当前模型，不记录每次运行

`Conversation.model` 只代表当前会话默认模型，但 assistant message 自身没有完整 run 视角。

这会导致后面很难回答这些问题：

- 这条回答到底用的是哪个模型
- 中途是否切换过模型
- 这次回答有没有跑工具
- 失败在哪一步
- token / latency / cost 是多少

#### 4. 单一 `upstream_file_id` 设计不够

`message_attachments.upstream_file_id` 现在是单字段缓存。

这对单 provider 勉强成立，但如果同一个附件需要：

- 在 `codex` 上传一次
- 在 `gemini` 再上传一次
- 或者不同 base URL / 不同账号 / file TTL 不同

单一 `upstream_file_id` 就不够用了。这里应该是“附件和 provider 文件引用”的一对多关系。

#### 5. RAG 目前是 SQLite + JSON embedding + Python 内存检索

当前知识库链路是：

- `knowledge_chunks.embedding_json` 存向量
- 查询时把 ready chunks 读出来
- `HybridRetriever.set_chunks(...)`
- Python 里做 cosine + BM25 + rerank

这说明现在不是“数据库不支持”，而是“向量检索根本没下沉到数据库/向量引擎”。数据量一大，RAG 成本会直接落在应用层。

## 3. 外部方案调研结论

这里重点看了三类东西：

- 厂商官方 API 怎么表达 thinking、多模态、流式、输入格式
- 通用 SDK 怎么做 provider 归一化
- 通用网关怎么做兼容层

### 3.1 OpenAI 的做法

OpenAI 现在比较值得参考的点有三个：

- Responses API 用统一 `input` item 模型承载文本、图片、文件
- reasoning 用 profile/effort，而不是简单布尔值
- conversation state 用 `previous_response_id`，把“续写哪一轮”从 message 拼接里抽出来

对我们最有价值的启发是：

- 后端内部应该优先有一个“统一输入 part 模型”
- reasoning 控制应该升级为 profile，而不是 `thinking_enabled`
- 流式事件也应该是 typed event，而不是只有 token/reasoning 两种

### 3.2 Anthropic 的做法

Anthropic Messages API 的关键特征是 content block 非常明确，常见 block 就包括：

- `text`
- `thinking`
- `tool_use`
- `tool_result`
- `image`
- `document`

它的流式也是围绕 block 来做，比如：

- `content_block_delta`
- `thinking_delta`
- `input_json_delta`

这对你现在的后端很有参考价值，因为它说明“thinking、多模态、tool call”本质上都应该被当成结构化内容块，而不是散落在不同 if 分支里。

### 3.3 Gemini 的做法

Gemini 的统一结构是：

- `contents[]`
- `parts[]`

同一个 `Part` 里可以承载：

- text
- inline data
- function call / function response
- thought

Gemini 在 function calling 上还提供了明确的模式控制：

- `AUTO`
- `ANY`
- `NONE`
- `VALIDATED`

这说明 tool policy 也不应该只是开关，而应该支持“禁止、可选、强制、强校验”这类策略。

### 3.4 Vercel AI SDK 的做法

Vercel AI SDK 这类通用 SDK 的优势不在于它比厂商 API 更强，而在于它把应用内协议抽象清楚了。它的思路大致是：

- UIMessage 和 ModelMessage 分层
- message content 用 parts 表达
- provider-specific 参数通过 `providerOptions` 隔离
- `streamText` / tool loop 统一事件处理

这类方案最值得学的点是：

- app 内部先定义 canonical schema
- provider-specific 差异往 adapter 下沉
- 上层业务不要直接理解厂商 wire format

### 3.5 LiteLLM 这类网关的做法

LiteLLM 这类网关的价值主要在：

- 快速把多 provider 暴露成近似统一接口
- 减少简单模型接入成本

但它的局限也很明显：

- 很多 provider-native 能力最终还是要额外参数或特判
- 越到 thinking、多模态、tool streaming 这些细节，统一表面越容易漏语义

所以它适合做：

- 边界网关
- 临时兼容层
- 非核心能力接入

不太适合直接当你应用内部的核心领域模型。

### 3.6 调研结论

更合理的方向不是“找一个统一 API 把所有厂商抹平”，而是：

- 在应用内部定义 canonical input / event / tool / capability schema
- 每个 provider family 做自己的 adapter
- mode 运行时只依赖 canonical schema

这也是你现在这套后端最缺的那一层。

## 4. 新方案总览

我建议的目标架构是：

1. 一个统一运行时 `RunOrchestrator`
2. 一套 canonical message / input part / stream event 协议
3. 一个 mode plugin 系统
4. 一个 provider adapter 系统
5. 一个 app tool runtime
6. 一个可迁移到 Postgres + pgvector 的持久化层

建议保留 FastAPI + SQLAlchemy，但重排目录职责。

### 5.1 目录映射建议

基于你当前目录，建议这样迁移，而不是一次性重写：

- `app/llm/*` -> 逐步迁到 `app/providers/*`
- `app/chat/streamer.py` -> 拆成 `runtime/orchestrator.py + runtime/events.py`
- `app/chat/history.py` 中与附件/多模态有关的内容 -> `context/attachments/*`
- `app/retrieval/*` -> 保留检索逻辑，但外层改挂到 `tools/*` 或 `context/retrieval/*`
- `app/debate/*` -> 变成 `runtime/modes/debate.py` 及其状态模块
- `app/storage/*` -> 逐步变成 `persistence/*`

## 6. 统一内部协议设计

### 6.1 Canonical Input Part

后端内部不要再直接围绕“某家 API 的 message payload”写业务。应该先定义统一输入 part。

建议内部至少支持这些 part：

- `text`
- `image`
- `document`
- `file_ref`
- `audio`
- `tool_call`
- `tool_result`
- `citation`

建议内部结构类似：

```python
class InputPart(TypedDict):
    type: Literal[
        "text",
        "image",
        "document",
        "file_ref",
        "audio",
        "tool_call",
        "tool_result",
        "citation",
    ]
    text: str | None
    mime_type: str | None
    storage_asset_id: str | None
    provider_file_ref_id: str | None
    metadata: dict[str, Any]
```

然后 `Message` 变成：

- role
- parts[]
- metadata

这样多模态 routing 就不再是散在 `chat/history.py` 的 if/else，而是 adapter 根据 capability 决定：

- 原生发送
- 先上传再发送
- 本地解析后退化成 text

### 6.2 Reasoning Profile

后端内部不要再传 `thinking_enabled: bool | None`，改成：

- `off`
- `auto`
- `low`
- `medium`
- `high`
- `max`
- `provider_default`

provider adapter 自己映射：

- OpenAI -> `reasoning.effort`
- Claude -> thinking budget / enabled
- Gemini -> thinking budget / include thoughts
- OpenAI-compatible provider -> 按 catalog 能力映射或关闭

前端短期仍然可以传布尔值，但 API 层应立即映射成内部 `reasoning_profile`。

### 6.3 Capability Matrix

用能力矩阵替代 `native_multimodal` 这类特化枚举。

建议每个模型能力至少描述这些维度：

- `input.text`
- `input.image`
- `input.pdf`
- `input.other_file`
- `input.audio`
- `transport.inline_base64`
- `transport.file_upload`
- `transport.remote_url`
- `reasoning.control`
- `reasoning.visible_trace`
- `reasoning.summary_only`
- `tools.function_calling`
- `tools.parallel_calls`
- `tools.forced_call`
- `stream.text`
- `stream.reasoning`
- `stream.tool_call`
- `stream.usage`
- `state.previous_response`

这样加新模型时，绝大多数情况只需要加目录项，不需要碰聊天链路。

## 7. Provider Adapter 设计

### 7.1 目标

Provider adapter 负责两件事：

- canonical message -> provider request
- provider stream event -> canonical stream event

上层 runtime 不应该知道某家 API 用：

- `messages`
- `contents`
- `input`
- `parts`
- `file_id`
- `document.source`

### 7.2 建议的接口

```python
class ProviderAdapter(Protocol):
    family: str

    def build_request(self, run: RunContext) -> ProviderRequest: ...

    async def stream(self, request: ProviderRequest) -> AsyncIterator[CanonicalEvent]: ...

    def capabilities(self, model_profile: ModelProfile) -> CapabilityMatrix: ...
```

### 7.3 建议的 family 划分

不要再把 adapter 粒度做成“每个厂商一个临时脚本”，建议按 API 家族划分：

- `openai_responses`
- `anthropic_messages`
- `gemini_generate_content`
- `openai_compatible`

这样：

- 同一家族新模型只改 catalog
- 新家族才需要新增 adapter

### 7.4 当前代码的迁移思路

可以直接复用现有实现逻辑，但位置要变：

- `openai_client.py` -> `providers/openai_responses.py`
- `claude_client.py` -> `providers/anthropic_messages.py`
- `gemini_client.py` -> `providers/gemini_generate_content.py`

`llm/service.py` 最终应该只剩：

- 读 model profile
- 找 adapter
- 调 adapter

不再负责 provider 特性分支。

## 8. Mode Plugin 设计

### 8.1 为什么必须做

你现在最容易继续长歪的点，就是 chat 和 debate 各有一套运行链。

正确做法是把“模式”定义成运行时插件，而不是定义成“另一套 endpoint + 另一套 LLM 流式逻辑”。

### 8.2 建议的 mode 抽象

每个 mode 至少负责：

- 如何组装系统指令
- 允许哪些工具
- 如何解释 stream event
- 如何更新状态
- 最终如何持久化

建议接口类似：

```python
class ModePlugin(Protocol):
    mode_name: str

    async def prepare(self, request: RunRequest, deps: RuntimeDeps) -> PreparedRun: ...
    async def on_event(self, event: CanonicalEvent, state: RunState) -> None: ...
    async def finalize(self, state: RunState) -> RunResult: ...
```

### 8.3 当前模式的落位建议

- `chat` 模式：单轮 assistant 生成，支持 context tools
- `debate` 模式：stage machine，但每个 speaker turn 仍然走统一 orchestrator

这样以后新增：

- 深度研究模式
- agent 模式
- 写作模式
- 代码模式

都不需要再复制一套 provider streaming 逻辑。

## 9. Tool Runtime 设计

### 9.1 把 retrieval_mode 升级为 tool policy

短期为了兼容前端，`retrieval_mode` 可以先保留。

但后端内部应改成：

- `tool_policy = off`
- `tool_policy = context_only`
- `tool_policy = model_optional`
- `tool_policy = force_search`
- `tool_policy = force_rag`

因为 RAG 和 Search 未来都应该是 tool runtime 的一部分，而不是只在回答前拼一条 system prompt。

### 9.2 工具分三类

建议把工具分成三类，不要混成一个概念：

#### 1. Context Providers

不暴露给模型直接调用，但会在回答前准备上下文：

- history
- memory recall
- file context

#### 2. App Tools

由你自己的后端执行：

- `rag_search`
- `web_search`
- `memory_lookup`
- 以后可能有 `workspace_lookup`

#### 3. Provider-native Tools

由模型厂商托管或原生支持：

- OpenAI hosted tools
- Anthropic tool use
- Gemini function calling

运行时应该统一接住 tool call，再决定：

- 由 app 执行
- 由 provider 托管
- 或回退为 context 注入

### 9.3 建议的工具循环

```text
Mode -> Orchestrator -> ProviderAdapter.stream()
     -> tool_call event
     -> ToolExecutor.run()
     -> tool_result message
     -> ProviderAdapter.stream(next turn)
```

这条循环一旦建立好，RAG/Search 未来就不再是特殊模式，而是统一工具体系的一部分。

## 10. 统一流式事件协议

### 10.1 当前问题

当前前端消费的 NDJSON 事件已经很清楚，但语义仍然偏窄，主要是：

- `meta`
- `status`
- `reasoning`
- `token`
- `sources`
- `context`
- `done`
- `error`

这对普通聊天够用，但对未来下面这些场景不够：

- tool call 实时展示
- tool result 展示
- usage / latency / cost
- structured output
- 多段 output part

### 10.2 建议的 canonical event

内部统一事件建议至少有：

- `run.started`
- `step.started`
- `status.updated`
- `reasoning.delta`
- `output_text.delta`
- `tool_call.delta`
- `tool_call.completed`
- `tool_result`
- `citations.updated`
- `usage`
- `run.completed`
- `run.failed`

### 10.3 前端兼容策略

这里不要大爆炸。

建议后端先做两层：

- 内部：canonical event
- 外部：`NDJSON v1 adapter`

`NDJSON v1 adapter` 继续输出当前前端能吃的：

- `reasoning`
- `token`
- `sources`
- `done`

这样你可以先重构后端，不用把前端一起拖进来。

## 11. 数据库与持久化新方案

### 11.1 选型建议

建议改成：

- 开发环境：SQLite 仅允许本地开发/测试
- 目标环境：PostgreSQL + pgvector
- 媒体/知识库文件：本地磁盘开发，生产可切 MinIO / S3

原因很直接：

- 现在已经有多用户、会话、记忆、知识库、附件、辩论、流式运行记录
- 还要加 tool trace、run steps、provider refs
- RAG 也已经不适合继续把 embedding 放在 JSON 里

如果继续把 SQLite 当目标数据库，后面会持续在“补丁式演化”里花时间。

### 11.2 建议新增的核心表

建议至少引入这些表：

- `users`
- `user_sessions`
- `conversations`
- `messages`
- `message_attachments`
- `message_sources`
- `message_artifacts`
- `runs`
- `run_steps`
- `run_events`
- `tool_calls`
- `provider_file_refs`
- `knowledge_documents`
- `knowledge_chunks`
- `memory_items`
- `memory_documents`
- `debate_sessions`
- `debate_turns`
- `debate_judgements`

### 11.3 关键表职责

#### `messages`

只保留稳定字段：

- role
- plain_text_content
- model_id
- conversation_id
- parent_message_id
- created_at

不要继续往里面塞越来越多 JSON。

#### `message_artifacts`

专门存派生内容：

- `reasoning_raw`
- `reasoning_summary`
- `attachment_brief`
- `context_snapshot`
- `structured_output`
- `brainstorm`

这样以后 artifact 变多，不用继续给 `messages` 补列或加 JSON。

#### `message_sources`

把引用源拆成行级结构：

- message_id
- source_type
- title
- path
- url
- domain
- excerpt
- score

#### `runs`

这是这次重构里最关键的新表之一。每次模型生成都应该有 run。

至少记录：

- conversation_id
- request_message_id
- response_message_id
- mode
- model_id
- provider_family
- reasoning_profile
- status
- started_at
- completed_at
- error_code
- error_message

#### `run_events`

用于调试、回放、审计、失败定位。

至少记录：

- run_id
- sequence_no
- event_type
- payload_json
- created_at

#### `provider_file_refs`

解决当前 `upstream_file_id` 单值不够的问题。

至少记录：

- attachment_id
- provider_family
- base_url_fingerprint
- remote_file_id
- remote_purpose
- expires_at
- created_at

### 11.4 知识库新方案

知识库建议至少改两件事：

- `knowledge_chunks.embedding_json` -> pgvector 列
- 相似度检索下沉到数据库层

第一阶段不一定非要上独立向量数据库，但至少不要继续：

- 读全量 chunk
- Python 内存计算 cosine

对于你当前这个项目体量，`Postgres + pgvector + rerank` 已经足够。

### 11.5 迁移方式

数据库迁移不要再靠启动时补列。

建议直接引入：

- Alembic

以后所有 schema 变更都通过 migration 执行。

## 12. 模型目录新方案

### 12.1 不再让 catalog 表达厂商特例

当前 `model_catalog.json` 里几个字段的问题是：

- `native_multimodal` 带厂商语义
- `thinking_mode` 只有简单 on/off 默认控制
- provider 实际是“路由方式”和“API 家族”混在一起

建议保留 catalog 文件，但改成下面这套语义：


### 12.3 新增模型时的理想成本

重构完成后，应该做到：

- 同 API 家族新增模型：只改 catalog
- 新增 provider family：新增 adapter + catalog

而不是像现在一样需要同时碰：

- catalog
- history 准备
- multimodal 路由
- thinking 兼容
- stream 解析

## 13. 分阶段落地路线

### Phase 0: 定边界，不大改接口

先做这些：

- 引入 `canonical events`
- 引入 `reasoning_profile`
- 引入 `ProviderAdapter` 接口
- 保留现有 NDJSON 输出

这一阶段不动前端协议，不动数据库大迁移。

### Phase 1: 抽 provider adapter

目标：

- 把 `app/llm/*` 重构成 `providers/*`
- `llm/service.py` 只做 registry 和 dispatch
- `chat/history.py` 不再直接理解厂商 wire format

验收标准：

- 新模型接入只需改 catalog
- 新 provider family 不再影响 chat/debate 业务逻辑

### Phase 2: 建统一 orchestrator

目标：

- `chat/streamer.py` 的编排职责拆出去
- 新增 `RunOrchestrator`
- `chat` 先接入

验收标准：

- 普通聊天完整走 orchestrator
- 现有接口和前端保持兼容

### Phase 3: 把 debate 改成 mode plugin

目标：

- `debate/streaming.py` 不再自己维护独立流式执行链
- 每个 speaker turn 也走 orchestrator

验收标准：

- debate 只保留状态机和 mode-specific prompt/state
- provider stream 消费不再重复实现

### Phase 4: 把 retrieval_mode 改造成 tool runtime

目标：

- RAG/Search 进入统一工具体系
- 保留老的 `retrieval_mode` API，但只当兼容层

验收标准：

- 后端内部不再把 RAG/Search 当特殊模式
- 工具链可以支持 model-driven tool call

### Phase 5: 数据库升级

目标：

- 引入 Alembic
- 增加 `runs/run_events/provider_file_refs/message_sources`
- 把知识库向量迁到 pgvector

验收标准：

- 可以追踪每次运行
- 可以按 run 回放错误
- 可以按 provider 保存多个 file ref

### Phase 6: 前端协议升级

这一阶段再做：

- richer stream event
- tool timeline
- usage/cost panel
- 更细的 capability UI

但这一步一定要放在后端完成 canonical event 之后。

## 14. 优先级建议

如果你现在就开始拆，我建议优先级是：

1. `ProviderAdapter + CapabilityMatrix + reasoning_profile`
2. `RunOrchestrator`
3. `chat` 模式迁移
4. `provider_file_refs + runs + run_events`
5. `debate` 模式迁移
6. `tool runtime`
7. `Postgres + pgvector`
8. 前端协议升级

这里最不建议的顺序是：

- 先重写前端
- 继续往 `chat/streamer.py` 和 `debate/streaming.py` 里堆分支
- 继续在 `model_catalog.json` 上加新的厂商特化字段

## 15. 未来功能如何落位

你提到的未来功能，正好可以作为这次架构是否合理的检验标准。下面是建议落位：

### 15.1 Mode Plugin 类功能

这类功能本质上是“新的交互模式”，不应该再各自长一套独立后端链路：

- 头脑风暴模式
- 游戏模式
- 播台模式
- 打电话那种聊天

建议都落在：

- `runtime/modes/*`

它们共享：

- provider adapter
- tool runtime
- stream event
- persistence/run tracing

只在 mode 层定义：

- prompt 策略
- 状态机
- 允许的工具
- UI 展示偏好

### 15.2 Context / Tool 类功能

这类功能更适合落在上下文与工具层：

- RAG 文件夹整理
- 压缩对话
- 接入一些有趣功能

建议落在：

- `context/history/*`
- `context/retrieval/*`
- `tools/*`

具体建议：

- `压缩对话`：做成 history compaction / summary service，而不是前端逻辑。
- `RAG 文件夹整理`：做成知识库 ingestion/indexing 策略，不要只是文件系统脚本。
- `接入一些有趣功能`：统一按 tool plugin 接入，不要直接塞进 chat 主链路。

### 15.3 Multimodal / Realtime 类功能

这类功能会影响输入协议和流式协议：

- AI 语音输入
- 打电话那种聊天

建议在 canonical input / event 里提前预留：

- `audio` input part
- realtime / duplex stream event
- turn state / vad / partial transcript

哪怕第一期不做实时通话，也不要把协议设计死成“只有文本 + 文件上传”。

### 15.4 Provider 扩展类功能

这类功能主要检验 provider adapter 是否设计正确：

- 适配国产模型

建议把“国产模型”拆成两类看：

- OpenAI-compatible 国产网关/模型服务
- 非 OpenAI-compatible 的原生 API 家族

如果 adapter 设计正确：

- 第一类大多只需要 catalog + provider preset
- 第二类新增一个 provider family adapter 即可

### 15.5 Infra 类功能

这类功能不属于 mode，也不属于 provider：

- 增加缓存

缓存建议分层，不要只说“加 Redis”：

- L1：进程内短缓存
  - model catalog
  - capability
  - provider model list
- L2：外部缓存
  - web search 结果
  - rerank 结果
  - query rewrite 结果
  - provider file ref
- L3：持久缓存
  - knowledge index
  - attachment brief
  - memory artifacts

未来如果上 Docker 化部署，建议：

- PostgreSQL + pgvector
- Redis
- app

这是比较稳的三件套。

## 16. Docker 与基础设施建议

既然已经决定目标数据库是 `PostgreSQL + pgvector`，建议现在就把部署形态一起定掉。

### 16.1 推荐的基础容器

建议至少有：

- `app`
- `postgres`
- `redis`

其中：

- `postgres` 使用 pgvector 镜像
- `redis` 先用于缓存和后续异步任务协调

### 16.2 为什么现在就要加 Redis

即使第一阶段还没有完整 tool loop，也建议把 Redis 纳入设计，因为后面这些都很容易用到：

- search/rag/query rewrite cache
- provider file ref cache
- stream session 临时状态
- 异步索引任务
- memory refresh 协调

如果现在不纳入，后面又会出现第二轮基础设施重构。

### 16.3 SQLite 的定位

重构后建议明确：

- SQLite：只用于本地最小开发环境/单元测试
- PostgreSQL：开发默认、部署默认、长期目标

不要再让 SQLite 同时承担“临时开发库”和“目标生产设计参考”。

## 17. 下一步最应该做什么

如果你问“下一步该干什么”，我的建议不是继续讨论，而是马上进入第一轮工程落地。

### Sprint 1：先把地基定住

第一轮只做四件事：

1. 引入 `PostgreSQL + pgvector + Redis` 的 Docker 开发环境
2. 定义后端内部基础协议：
   - `ReasoningProfile`
   - `CapabilityMatrix`
   - `InputPart`
   - `CanonicalEvent`
3. 搭 `providers/` 骨架，把现有 `llm/*` 包一层 adapter registry
4. 新增 `runs / run_events / provider_file_refs` 的持久化模型与 migration

这一轮先不要碰：

- 前端重构
- debate 模式重写
- tool loop 全量改造
- 头脑风暴/游戏/播台等新模式实现

因为这些都依赖地基。

### Sprint 1 的验收标准

做完第一轮后，至少应满足：

- 本地可以一键起 Docker：
  - app
  - postgres(pgvector)
  - redis
- 新老聊天接口还能跑
- 每次回答都有 run 记录
- 附件支持 provider 级 file ref，而不是单一 `upstream_file_id`
- 新模型 capability 不再只靠 `native_multimodal` 表达

### Sprint 2：再抽聊天编排

第二轮再做：

- `RunOrchestrator`
- `chat` 模式迁移
- NDJSON 兼容层

### Sprint 3：再处理 debate 和 tools

第三轮再做：

- `debate` mode plugin
- retrieval_mode -> tool policy
- cache 分层落地

## 18. 我对你这个项目的明确建议

如果只给一个结论，我建议是：

- 后端内部立刻从“provider 分支式架构”转向“canonical schema + adapter + mode plugin”架构
- 数据库目标改成 `Postgres + pgvector`
- 短期保留当前 NDJSON 前端协议，用兼容层兜住
- RAG/Search 后端内部改造成工具体系的一部分

你当前代码不是完全没重构，而是“重构到一半停在中间态”：

- 已经有领域模块
- 已经有 model catalog
- 已经有 retrieval/memory/multimodal 独立目录

但最关键的统一层还没补上：

- 统一运行时
- 统一输入模型
- 统一流式事件
- 统一工具循环
- 统一 run 持久化

这几层补上之后，后面再加模型、加模式、加工具，成本会明显下降。

## 19. 可直接执行的下一步

如果按最务实的方式推进，我建议下一轮先做这三件事：

1. 先定义内部 `CapabilityMatrix / ReasoningProfile / CanonicalEvent / InputPart`
2. 把 `app/llm/*` 重构为 `providers/*`，让 `llm/service.py` 只剩 registry
3. 引入 `runs + provider_file_refs`，先不动前端

这三步做完，后面无论继续拆 chat、debate，还是切数据库，都会顺很多。
