# 附件与多模态

更新时间：2026-04-27

## 1. 功能范围

聊天支持上传附件，后端根据模型能力决定处理方式。

支持类型包括：

- 图片
- PDF
- DOCX
- XLSX
- CSV
- TSV
- Markdown
- 普通文本

当前不再使用本地 OCR 或本地视觉模型。

## 2. 前端入口

关键文件：

- `frontend/src/features/chats/ui/ChatComposer.tsx`
- `frontend/src/features/chats/ui/composer/ComposerAttachmentStrip.tsx`
- `frontend/src/features/chats/ui/message/MessageAttachmentStrip.tsx`

前端会根据模型能力控制上传入口。

## 3. 后端保存

附件上传后：

1. 保存到 `MEDIA_ROOT`。
2. 写入 `message_attachments`。
3. 关联到 user message。
4. 根据模型能力生成上下文或原生多模态输入。

关键文件：

- `backend/app/storage/media.py`
- `backend/app/chat/context.py`
- `backend/app/multimodal/attachment.py`

## 4. 轻量文件解析

当模型不支持原生文件输入，或文件类型需要本地抽取文本时，后端使用轻量解析器。

关键文件：

- `backend/app/multimodal/file_parser.py`
- `backend/app/multimodal/file_types.py`

解析结果进入：

- `attachment_context`
- `file` 类型 source
- 最终 system context

## 5. 原生多模态模式

模型目录字段：

```text
native_multimodal
```

支持值：

- `false`
  - 不走原生多模态，只用文本上下文。
- `codex`
  - 图片作为原生多模态输入。
- `gemini`
  - 图片和支持文档走 Gemini 原生协议。
- `claude`
  - 图片和支持文档走 Claude 原生协议。

## 6. DeepSeek 当前策略

当前 DeepSeek 默认：

- 禁用图片上传。
- 不走 OCR。
- 不走视觉模型。
- 文本类附件仍可解析为普通文本上下文。

这避免了“DeepSeek 不支持图片但前端还能传”的错配。

## 7. 配置

```env
ATTACHMENT_MAX_UPLOAD_COUNT=8
ATTACHMENT_MAX_UPLOAD_SIZE_BYTES=20971520
ATTACHMENT_PROCESSING_MAX_CONCURRENCY=2
FILE_TEXT_MAX_CHARS=6000
FILE_TABLE_ROW_LIMIT=40
FILE_TABLE_COLUMN_LIMIT=24
IMAGE_TEXT_MAX_CHARS=4800
```

## 8. 当前边界

- 图片 OCR 已移除。
- 不做本地视觉理解。
- 大型 PDF/Excel 只做轻量抽取，不保证完整结构还原。
- 原生多模态能力完全取决于模型目录和上游 provider。
