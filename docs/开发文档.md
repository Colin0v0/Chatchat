### 0.0 当前部署口径

当前主线已经切到纯 CPU + 云端 API 模型：

- DeepSeek 聊天走 `DEEPSEEK_BASE_URL` / `DEEPSEEK_API_KEY`
- embedding、rerank、ASR、云端 TTS 默认走 `DASHSCOPE_API_KEY`
- 数据库和缓存仍建议用 Docker 本地部署：PostgreSQL + pgvector + Redis
- 后端不再加载 Ollama、本地 OCR、本地视觉模型、本地 ASR、本地 embedding、本地 reranker
- 浏览器本机音色仍保留，它只是播放端能力，不属于后端本地模型推理

部署细节、服务器规格和环境变量说明见 `docs/部署与模型接入.md`。

### 0.1 当前总体状态

Chatchat 当前已经进入“前端逐步 feature-first、后端 runtime-first”的阶段：

- 前端已经建立 `features/ + shared/` 骨架，`auth / workspace / models / knowledge / memories` 迁移已基本成型。
- 前端仍保留两个明显的过渡中枢：
  - `frontend/src/features/workspace/model/useChatApp.ts`
  - `frontend/src/lib/api.ts`
- 后端已经完成统一 runtime 主链，`chat` / `debate` 不再各自维护独立的底层流式执行骨架。
- 后端基础设施已经切到 `PostgreSQL + pgvector + Redis + Alembic`，SQLite 只剩少量测试夹具。
- 模型接入不再保留本地模型 family；新增模型优先通过云端 API provider 和 `backend/model_catalog.json` 扩展。

### 0.5 当前聊天主链路

现在一轮聊天的大致真实链路如下：

1. 前端在 `useChatApp` 内组装当前会话、模型、`tool_mode`、`reasoning_profile`、附件。
2. `frontend/src/lib/api.ts` 仍作为过渡 API 入口，组装 `FormData` 请求 `/api/chat/stream`。
3. `backend/app/api/chat.py` 接收 `tool_mode`、`reasoning_profile`、附件文件。
4. `backend/app/application/chat_preparation.py` / `chat_requests.py` 负责把 HTTP 请求整理为内部运行请求。
5. `backend/app/application/chat.py` 通过 `stream_mode_action()` 进入统一 mode runtime。
6. `backend/app/runtime/modes/chat.py` 调用统一 orchestrator。
7. `backend/app/runtime/orchestrator.py`
   - 准备历史消息
   - 计算 context strategy
   - 调用 memory prompt
   - 调用 `ToolRuntimeService`
   - 建立 run trace
8. `backend/app/runtime/model_runner.py` 统一执行 provider stream。
9. `backend/app/providers/*`、`provider_transports/*`、`provider_codecs/*` 负责厂商差异适配。
10. 统一 canonical event 再编码成 NDJSON 返回前端。
11. 结果落库到 `messages`，运行痕迹落库到 `runs / run_events`。

- `api/debate.py`
- `application/debate.py`
- `runtime/modes/debate.py`
- `runtime/modes/debate_*`

当前已经拆出的 debate 子模块包括：

- `debate_execution.py`
- `debate_state.py`

- `debate_policies.py`

这意味着 debate 现在主要保留 mode-specific 的状态推进、judge 逻辑和落库规则，而不是重复实现 provider stream 消费。

### 0.8 当前模型与请求语义

当前模型目录不再是“少量布尔位 + provider 特判”，而是 capability-first：

- 唯一真源：`backend/app/providers/catalog.py`
- 数据真源：`backend/model_catalog.json`
- 前端模型接口：`/api/models`
- 当前显式控制项：
  - `tool_mode = none / knowledge / search`
  - `reasoning_profile = off / auto / low / medium / high / max / provider_default`

当前 provider 口径：

- `openai` family 当前主要承载 DeepSeek 这类 OpenAI-compatible API
- `codex` / `gemini` / `claude` 仍是云端 provider
- 百炼/DashScope 不作为聊天 provider 出现在模型列表里，主要服务 embedding / rerank / ASR / TTS
- DeepSeek 模型在 catalog 中关闭图片上传，文件类附件仍可先经轻量解析器转成文本上下文

当前后端仍保留一部分过渡兼容：

- `llm/thinking.py` 里仍有 prompt 注入式 reasoning 兼容
- `native_multimodal_mode` 仍是过渡字段，还没有完全被更高层的统一输入协议替换

### 0.9 当前开发优先级

如果你现在要继续开发，请优先遵守下面的方向：

1. 新功能优先落在现有 feature / runtime / provider 分层中，不要把新逻辑塞回旧全局入口。
2. 前端新增请求优先考虑直接建 `features/*/api/*`，不要继续扩 `lib/api.ts`。
3. 后端新增模式优先走 `runtime/modes/*`，不要再新建一套平行流式执行链。
4. 附件、run trace、模型能力相关能力优先沿用现有表和 canonical event，不要再加新的隐式旁路。

## 1. 当前产品形态

Chatchat 现在是一个“带登录、多模型、多模态、检索、记忆”的聊天工作台。

当前已经落地的功能：

- 账号密码登录
- Cookie Session 鉴权
- 多用户隔离的会话与记忆
- 多模型聊天
- reasoning / thinking 流式展示与持久化
- 多用户隔离的知识库 RAG 检索
- Web Search
- 图片和文件上传
- 本地附件解析链路
- 原生多模态上游上传链路
- 语音录音与转写
- Memory 面板、候选记忆、记忆文档

当前明确不做的事情：

- 不开放注册
- 不把业务逻辑继续堆进 `main.py`
- 不维护大量隐式 fallback
- 不为同一能力维护三套并行实现

## 6. 聊天主链路

当前一轮聊天大致流程如下：

1. 前端输入文本/附件
2. `frontend/lib/api.ts` 组装 `FormData`
3. 请求 `POST /api/chat/stream`
4. 后端 `chat/workflow.py` 创建 conversation/user message
5. 保存附件到 `message_attachments`
6. `chat/streamer.py` 先输出 `meta`
7. `MessageHistoryService` 准备历史消息
8. 如需要，本地附件上下文先补齐
9. `RetrievalService` 按 `retrieval_mode` 构造上下文
10. `MemoryService` 生成 memory prompt
11. `llm/service.py` 调用实际模型
12. 流式输出：
    - `status`
    - `reasoning`
    - `token`
    - `sources`
    - `context`
    - `done`
13. 保存 assistant message
14. 后台异步调度 memory refresh

## 7. Thinking / Reasoning 逻辑

当前 thinking 逻辑是“后端标准化，前端展示”。

### 7.1 后端处理方式

后端会兼容两种来源：

- 上游直接返回 reasoning 字段
- 正文里混入 `<think>...</think>`

处理结果：

- 流式事件统一发 `reasoning`
- 正文只发 answer token
- `done` 前保存完整 `reasoning_content`

### 7.2 前端处理方式

前端：

- 逐步展示 reasoning 面板
- 正式 answer 开始输出前，reasoning 流状态结束
- reasoning 内容仍保留，可展开
- 刷新历史会从 message.reasoning 恢复

## 8. 检索架构

### 8.1 当前模式

前端只传显式模式：

- `none`
- `rag`
- `web`

后端不再依赖一套复杂 planner 来决定“要不要查”。

### 8.2 `RetrievalService`

负责：

- 生成 `RetrievalPlan`
- 并行执行 RAG / Web / 文件上下文
- 合并来源
- 对不同来源打分
- 生成注入模型的 system context

### 8.3 RAG

当前 RAG 已经改成“每个用户自己的知识库”：

- 只接受用户上传的 `.md`
- 文件按用户隔离存储在 `storage/knowledge/`
- 支持批量上传、批量删除
- 上传时只落盘和入库，不立即切分
- 点击“更新知识库”后才批量切分、embedding、写入 chunk
- 默认 embedding 模型为 `qwen3-embedding:0.6b`
- 默认 rerank 模型为 `dengcao/Qwen3-Reranker-0.6B:Q8_0`
- 检索前会做一层 RAG 查询重写，把“那一段 / 上面那个方案”改成更完整的知识库查询
- 分块后写入 `knowledge_chunks`
- 检索时严格按 `user_id` 过滤
- 不再维护全局笔记目录扫描和 `index.json`

关键文件：

- `knowledge/service.py`
- `retrieval/query_rewrite.py`
- `retrieval/rag/chunking.py`
- `retrieval/rag/retriever.py`

### 8.4 Web Search

请求使用 `enable_search=true` 和 `search_options.enable_source=true`，从 `output.search_info.search_results` 读取来源。

## 9. 多模态与附件链路

## 11. Memory 系统

### 11.1 当前组成

- `MemoryStore`
- `MemoryService`
- `MemoryExtractor`
- `memory_search` FTS
- `memory_documents`

### 11.2 当前 prompt 注入

Memory 注入不是直接把所有 memory 都塞给模型，而是：

- 先召回 relevant hits
- 再加载 memory documents
- 构造成 system prompt 注入

### 11.3 当前后台刷新

assistant 回答结束后会异步调度 memory refresh。

当前已经做的稳定性控制：

- 同一会话只保留最新 refresh task
- 旧任务会取消
- 有 `memory_refresh_max_concurrency` 并发上限

## 11.4 RAG 查询重写

RAG 查询重写是知识库检索前的一层文本预处理，不是新的检索模式。

作用：

- 结合最近几轮对话
- 把代词、指代和省略信息补全
- 输出一个更适合知识库召回的独立查询

当前配置项：

- `RAG_QUERY_REWRITE_ENABLED`
- `RAG_QUERY_REWRITE_MODEL`
- `RAG_QUERY_REWRITE_HISTORY_MESSAGES`

当前行为：

- 只在 `rag` 模式启用
- 只影响知识库检索 query
- 原始用户问题不会被替换
- debug context 里会记录是否应用了重写

## 14. 会话列表与前端状态保护

### 14.1 会话列表

以前会话列表为了拿最后一句 preview，会把整段消息历史都加载出来。

现在：

- 查询逻辑收口到 `storage/access.py`
- 只查摘要所需字段
- API 层不再做复杂查询拼接

### 14.2 前端最新请求保护

当前前端很多地方都有“只接受最后一次异步请求结果”的需求。

现在统一由：

- `frontend/src/app/useLatestRequestGuard.ts`

复用到：

- `useAuthSession.ts`
- `useChatApp.ts`
- `useMemoryManager.ts`

这样避免：

- 旧请求覆盖新状态
- 切会话后页面回跳
- memory 面板打开/关闭时状态错乱

## 17. 开发约定

继续开发时默认遵循：

1. 领域逻辑往对应目录收，不往 `main.py` 和路由层回堆
2. 有重复状态保护时，优先抽 hook / helper
3. 有重复查询时，优先下沉到 `storage/access.py`
4. 多模态能力判断只认 `native_multimodal`
5. 不随意新增 fallback 分支
6. 前后端协议字段名改动时一次收干净
